# Source: live diagnostic, not a dump. 0x42C accepted writes and held them
# with no visible effect; 0x3EC reads back 0.00, which is what an unlocked
# LockedFov holds, and it matches the Xbox pattern of DefaultFOV+4
# (Xbox: DefaultFOV 0x3C0 / LockedFov 0x3C4, Steam: 0x3E8 / 0x3EC).

# Xbox table unchanged and NOT stale - its LockedFov was already correct.
#
# Note for the next dump: writing LockedFov alone does nothing. The engine
# only copies it into the POV when the unreflected bLockedFOV bit is set.
# That bit lives in the bool bitfield word shared with
# bDefaultConstrainAspectRatio / bClientSimulatingViewTarget /
# bUseClientSideCameraUpdates / bGameCameraCutThisFrame. If a dump can give
# its byte and bit, the runtime probe in Loop.hpp can be retired.

# Correction (not a dump ingestion) - 2026-08-21
# Steam: slot index is (base + adj) & 3, NOT base ^ adj
# Steam: class/outer slots now decode WITHOUT the trailing ROL64(32)
#
# SUPERSEDED IN PART, SAME DAY: this entry first recorded OUTER_ADJ 1 -> 3.
# That was wrong. See the amendment at the end of this block - the constant
# stays at 1 and it is the operation that changes.
#
# Source: live read-only slot probe (Reflection::ProbeObjectSlots), three
# object types in one raid. All four slots decoded per object, then graded
# against name resolution, which already worked and so served as ground truth.
#
#   object               base  ^0 class            ^2 name (CI)          ^3 outer                 ^1
#   PlayerCameraManager    1   PlayerCameraManager  PlayerCameraManager   PersistentLevel          empty
#   LocalPawn              3   BP_PioneerCharacter_C BP_PioneerCharacter_C PersistentLevel         empty
#   UWorld                 3   World                BuriedCity_01_P       /Game/.../BuriedCity_01_P empty
#
# Two findings:
#
# 1. The outer slot was landing on the one slot of the four that is always
#    empty - sixteen zero bytes in every object probed. See the amendment
#    below for the correct rule; the first reading of this was wrong.
#
# 2. The trailing ROL64(32) in the PCLMUL slot decrypt is presentation, not
#    decryption. It moves the FName comparison index into the low half so name
#    slots can take it with a truncating cast. Pointer slots must use the
#    pre-rotation value. Applying the swap to a pointer is what turned a
#    perfectly good 0x91B8AF00 into 0x91B8AF0000000000 - the value that made
#    ClassPrivate look broken for the whole v818 cycle.
#
# _dump/fname_post.txt says "full u64 = pointer for class/outer slot" against
# the rotated value, which is wrong for this build - its own GetClassPtr bounds
# check would have rejected its own output. Its constants are all correct
# though, including OUTER_ADJ = 1; only the XOR it describes is wrong, and
# every other value it documents (hash constants, slot base/stride, both CLMUL
# polynomials, NAME_XOR = 2, CLASS_ADJ = 0) is confirmed.
#
# Propagated: GetClassName in Decryptions.hpp was casting ClassPrivate's return
# to an FName comparison index. It is a UClass*, so the name needs a second
# lookup on the pointer. That path had never worked.
#
# Xbox NOT stale and NOT affected: different pipeline entirely (slot base 0x10
# stride 0x10, two module XOR keys plus PSHUFLW, no CLMUL, no final rotate).
# FLAG for whenever an Xbox capture exists: Xbox ClassPrivate and OuterPrivate
# both call UObjectDecryptSlot_Xbox with the same unadjusted slot index, so
# they return the same value. Steam needs three distinct indices, so one of the
# two Xbox paths is likely wrong - but there is no live Xbox capture to grade a
# fix against, so nothing was changed.
#
# ---- Amendment, same day, second probe run ----
#
# The slot index is (base + adj) & 3. It is not an XOR, and OUTER_ADJ stays at
# the dump's value of 1.
#
# The first run covered bases 1 and 3 only, and base^3 == (base+1)&3 for both
# of those, so "XOR 3" fit the data and was recorded. A second run caught
# UWorld at base 0, where the two rules diverge - XOR 3 predicts slot 3, which
# is empty, while ADD 1 predicts slot 1, which holds the map package. Six
# observations across bases 0, 1 and 3 now fit ADD and only ADD.
#
#   base  class(+0)  name(+2)  outer(+1)  empty(+3)
#     0       0          2         1          3
#     1       1          3         2          0
#     3       3          1         0          2
#
# Class and name were never affected: adding 0 or 2 to a 2-bit value gives the
# same result as XOR-ing it, so those two constants read identically under
# either rule. Outer is the only one that can distinguish them, and only when
# base is 0 or 2 - which is why one raid's worth of samples was not enough.
#
# Selection now goes through UObjectSlotFor_Steam so all three call sites share
# one rule. Lesson for the next probe: sample until every base value 0-3 has
# been seen before believing a slot rule.
# ============================================================
